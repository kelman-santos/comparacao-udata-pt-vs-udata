Problemas que os dois lados resolveram cada um à sua maneira

Pelos changelogs, estes pares parecem atacar o mesmo problema. Confirmar caso a caso no sync: pode bastar ficar com a versão upstream e largar a nossa.

  • IDs de recursos harvestados: o fork mantém o id entre harvests (16.0.0.7) e o upstream deixou de adotar remote ids CKAN (17.5.0), além de deduplicate-resource-ids.
  • Filtro de várias tags: o fork passou a OR (16.0.0.7, breaking) e o upstream corrigiu "filter with multiple tags" (17.0.8).
  • HTTP dos harvesters: o fork usa uma sessão protegida com retries e oculta credenciais; o upstream tem cliente anti-SSRF (17.2.0) e deixou de partilhar headers entre fontes (17.19.0).
  • Índice de harvest.remote_id: migração do fork de 10 jul, e backfill upstream de 17 ago.
  • Avatares: o fork removeu o endpoint de identicon e o upstream limitou o tamanho do avatar (17.21.0).
  • Validação de uploads: o fork valida o conteúdo dos uploads em streaming; o upstream valida o conteúdo das imagens (17.7.1) e faz streaming dos uploads (17.6.0).

Outras observações

A versão voltou a desalinhar

A tag v16.0.0.13 (27 out) aponta para um commit cujo pyproject.toml diz 16.0.0.12 e cujo CHANGELOG não tem secção 16.0.0.13. O origin/main continua com 16.0.0.12. A proteção "refuse to tag a version the project does not declare" ainda está em Unreleased, por isso chegou depois desta tag.

  • Ficheiros que não deviam estar em main: t.json, test-results/.last-run.json, logs/.gitkeep, package.json e package-lock.json.
  • Números desatualizados em docs/versioning.md: o texto fala em 286 ficheiros (114 novos, 172 modificados). Hoje são 343 (148, 187, 8).
  • O ramo feature/gateway-api-key: o upstream mexeu na mesma zona: âmbito sysadmin nos API tokens e migração rename-api-token-admin-scope (17.28.0), sessão recente para criar tokens (17.27.0), sem sessão em pedidos por API key (17.26.0). Convém alinhar o desenho com isto para não criar mais um conflito.

Recomendação

  1. Sincronizar para v16.6.1 primeiro. São 41 conflitos, sem breaking changes, e a versão passa a 16.6.1.1.
  2. Tratar a v17.0.0 como uma etapa isolada. Rever os 7 harvesters PT contra a nova API de harvest, com testes de preview de cada fonte real.
  3. Avançar até à 17.x atual em uma ou duas etapas (por exemplo 17.14.0 e depois main). Em cada par da secção "Onde os dois lados se cruzam", preferir a solução upstream sempre que cubra o caso português, porque cada ficheiro que deixa de ser modificado é um conflito a menos no sync seguinte.
  4. Antes de cada etapa, correr as 29 migrações upstream sobre uma cópia da base de dados de ppr. Nenhuma migração reverte.
